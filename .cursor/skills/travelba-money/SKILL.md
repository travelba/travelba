# Travelba — argent

Le CRM tient un **grand livre**. Carte, Apple Pay et prélèvement SEPA passent par Stripe. Les virements arrivent sur Revolut Business et se rapprochent dans l’inbox.

## Encours

Vue `crm_customer_balances` = somme crédits `posted` − débits `posted` (par devise).

- Positif = avoir / **crédit disponible**
- Négatif = reste à payer
- Le grand livre stocke le signe. Dans **Transactions**, la carte d’origine affiche ce signe (encours, barre, mouvements). Le « % réglé » compte tous les débits postés. Le règlement Société / Particulier se place sous la barre, sans remplacer la carte ni le solde signé.

**Commission d’agence** (`agency_fee_rate`, défaut **10 %**, choix **7,5 %** ou **5 %** ; case `agency_commission` sur le voyage, défaut **false**) : le dossier gagne sur le compte ; un compte vide ou un dossier sans dérogation vaut 10 %. Si la case est cochée, `syncAgencyCommission` poste **une** ligne de dépense par réservation, `kind=adjustment` `external_id=booking:{id}:agency-commission`, libellé client « Commission d’agence » (sans le pourcentage). Le montant est ce taux des **étapes actives** (prix vendu du séjour, chauffeur, VIP Airport, visa, enregistrement) **et des dépenses supplémentaires**. Une étape annulée ou remplacée sort. Un aller-retour ne compte qu’une fois. Hors assiette : la ligne de commission elle-même, les frais de billeterie, tout crédit. Le client qui règle l’hôtel sur sa carte : le prix de l’étape compte quand même. La ligne se recalcule à l’ajout, la modification et le retrait. Elle ne majore pas chaque dépense, ne retire pas le montant global du séjour et n’entre pas dans le total stocké. Le prix affiché et le règlement utilisent la même assiette. Elle reste hors carnet. Postée seulement si le dossier est **Visible** et pas annulé. Décocher ou annuler → `void` (ou suppression des débits à l’annulation). Le virement Revolut est crédité **en entier** — plus de débit `{revolut_id}:agency-fee` au rapprochement. Les anciennes lignes de frais prises sur un crédit ont été retirées. Le crédit disponible est l’avoir positif du grand livre.

Ledger visible côté client (`/mon-compte/transactions`) : lignes `posted` seulement (RLS). L’agence ouvre **la même lecture** depuis `/admin/transactions/client/[id]` (fiche client « Transactions du client », nom du client ou bouton « Vue client » dans Argent › Grand livre). Les débits de dossier y apparaissent ; la liste agence reste limitée aux virements crédit. Chaque débit rattaché à un séjour nomme les voyageurs cochés sur la carte (`party_keys`, passagers, chambres), sinon les voyageurs du dossier, sinon rien. Ligne repliée : « Voyageur : … » ou « Voyageurs : A, B +N ». Le détail, le PDF du relevé et `grand_livre.voyageurs` listent tous les noms.

**Société** : si `company_role=member`, le client ne voit que les **débits** de ses dossiers (pas les crédits / encours société, pas le carnet de l’admin). `company_role=admin` = grand livre complet de **son** wallet. Il voit les carnets publiés de ses collaborateurs, pas ceux des autres admins. Un règlement crédite son wallet. Débits résa → `billing_customer_id` du dossier.

**Droit de dépense** (`spending_allowance`, null = pas de plafond) : l’agence le saisit sur la fiche, en euros, pour l’admin et chaque collaborateur. Un seul wallet. Le virement crédite l’admin. Le droit consommé = débits postés des dossiers de cette personne sur le compte crédit (un crédit rattaché à un dossier crédit le rend). Une dépense Pro ne le consomme pas et la carte de ce séjour n’affiche pas de reste. Le montant global affiché sur la carte est le prix du séjour. Si au moins un droit est fixé, `/mon-compte/transactions` montre une carte par séjour (montant, compte de rattachement, reste) et le détail des mouvements au clic. Le collaborateur ne voit que ses séjours : son encours restant est en grand, son droit de dépense en petit. L’admin voit l’encours société en grand, et sur chaque pastille le reste en grand, le droit en petit. Sinon l’écran actuel. Le droit de dépense n’est pas un second solde. S’il y a crédit et Pro, ces deux soldes restent au-dessus. Le collaborateur ne règle pas.

PDF relevé : bouton **Demander un relevé** sur `/mon-compte/transactions` (et la même lecture admin). Au clic, **Télécharger le PDF** ou **Recevoir sur WhatsApp**. Le PDF reprend l’encours signé, les dépenses, les règlements et les mouvements comptabilisés, avec les mentions de l’agence. Ce n’est pas une facture. Pas d’e-mail automatique. Le collaborateur `member` n’a pas ce bouton. WhatsApp part du numéro de la fiche ouverte (le contact, pas un autre admin de la société). Chaque essai est écrit dans `crm_whatsapp_messages` (`template_key` `releve` ou `releve_session`, `dedupe_key` `releve:{client}:{jour}`), y compris un échec. Hors fenêtre de 24 h, le PDF part avec le modèle Utility `releve` (`TWILIO_CONTENT_RELEVE`, en-tête Document) ; sans ce modèle, rien n’est envoyé et l’écran le dit. Dans la fenêtre, le message de session joint le PDF via `/api/whatsapp/releves/`. Sans téléphone, le fichier reste à télécharger — sur le téléphone du client, le partage peut encore joindre le PDF à WhatsApp. Aucune URL signée dans la page. L’outil MCP `envoyer_releve` fait ce même envoi (auteur : le jeton). Un second envoi réussi en cinq minutes est refusé, sauf `force`.

## Débit réservation

`syncBookingDebit` (`lib/crm/bookings.ts`) :

- Le grand livre client liste les **dépenses** (carte, frais de billeterie, chauffeur), pas la ligne « Réservation … ». Sous chaque dépense liée à un dossier : « Dans le cadre de {titre} ». Le montant global du séjour (`external_id` null) est retiré dès qu’une **carte** du même dossier est postée (`dropCoveredStayRollup`). Le frais de billeterie, la commission d’agence et la dépense libre ne le retirent pas. Le « % réglé » compte **tous** les débits postés du wallet, y compris un séjour encore au livre : la liste peut masquer ce séjour, la barre non.
- Crée / met à jour un débit `kind=booking` si le séjour est **Visible** (`visible_to_client`), `total_amount > 0` **et** `include_in_ledger` (défaut **true**), seulement tant qu’aucune dépense du dossier n’est au livre. Le statut stocké (`draft`, `quoted`, `confirmed`) ne décide pas du débit. Enregistrer pendant que le séjour est caché : **pas** de débit. Cacher le séjour retire le débit ouvert. Une annulation retire les débits.
- `cancelled` → supprime les **débits** `booking_id` (plus au grand livre). Les crédits et les virements Revolut restent rapprochés.
- `total_amount <= 0` **ou** `include_in_ledger=false` alors qu’un débit ouvert existe → `void` ce débit seulement
- Suppression du dossier → le même nettoyage des débits, puis delete de la réservation
- Séjour caché (`visible_to_client=false`) ou archivé → pas de débit
- Case admin « Inclure dans les transactions » à côté du montant du séjour. Décochez = prix carnet sans impacter l’encours.
- **Le client règle ce séjour** (`client_settles_stay`, défaut **false**) : l’hôtel est payé sur la carte du client, l’argent ne passe pas par l’agence. Le montant du séjour et les débits des cartes qui le composent (hôtel, vol, etc.) passent en `void`, même si « Inclure dans les transactions » est coché. Ils disparaissent de `/mon-compte/transactions` et de `/admin/transactions/client/[id]`. Le prix reste au carnet. Aucune ligne « réglé sur votre carte ». Restent au livre : la commission d’agence si la case est cochée, frais de billeterie, dépenses libres, et extras (chauffeur, VIP Airport, visa, enregistrement) seulement s’ils sont inclus. Pas d’encaissement Stripe.
- **Total séjour stocké** (`total_amount`) = **toujours** la somme des prix vendus des cartes (`item.amount` ; **vol** = unitaire × `details.ticket_count`, sauf `details.amount_is_total` où le montant stocké est déjà le total du groupe, au centime ; **une fois** pour l’aller-retour, chaque vol s’il est aller simple). Pas de saisie séparée, pas la somme des montants PDF. Carte sans prix = 0. `syncBookingTotalFromItems` à chaque enregistrement de dossier et à chaque POST/PATCH/DELETE carte. Chauffeur / greeter et frais billeterie (25 € par passager) **hors** ce total stocké. Le **prix affiché** « Montant du séjour » (réservation client, liste client, liste agence, dossier) ajoute la commission d’agence (taux du dossier, sinon du compte, sinon 10 %), les frais de billeterie et les dépenses libres. La commission porte sur les étapes (séjour + extras) et les dépenses, pas sur la billeterie. Ce chiffre est celui du règlement quand les frais suivent le séjour. On ne réécrit pas ces montants dans `total_amount` : l’assiette de la commission et le débit séjour resteraient faux.
- Carte (`item.amount`) : case **Inclure dans les transactions** (`include_in_ledger`, défaut **false**). `definir_visibilite_carte` (`inclure_transactions`) fait cette case, sans message, et le débit d’un vol `amount_is_total` est le total exact. Si cochée, débit `kind=booking` `external_id=booking:{id}:item:{itemId}`. Indépendant du montant du séjour — décochez le séjour pour ne pas compter deux fois. Recocher après un `void` **réactive** la même ligne (unique `external_id`) ; ne pas réinsérer. Libellé hôtel = nom d’établissement. Index unique : **un** débit séjour (`external_id` null), **plusieurs** cartes.
- **Dépense libre** (`kind=expense`) : bloc **Dépenses** du dossier, libellé + montant. Absente de l’itinéraire, du calendrier et du total stocké. Elle entre dans le prix affiché du séjour. `include_in_ledger` forcé. Débit `external_id=booking:{id}:expense:{itemId}`. Elle **ne retire pas** le montant global du séjour. Postée seulement si le séjour est **Visible**. L’import PDF ne crée pas ce kind. Sur la réservation client publiée, la section **Dépenses** (lecture seule, sous le montant du séjour) liste ces lignes et la commission d’agence si la case est cochée. Le libellé client est « Commission d’agence », sans le pourcentage. Le séjour publié suffit : le drapeau `visible_to_client` de la carte ne les masque pas.
- **Raccourcis** (`crm_expense_presets`, Réglages › Dépenses types, outil `depenses_types`) : un clic ajoute une dépense libre, quantité 1, libellé et montant du raccourci, même chemin que le formulaire. Défauts tant que la table n’est pas en place : Frais billetterie 25 € (`guard=ticketing`), Frais billetterie train 10 €, Frais transfert 10 €. Une table vide ne les remet pas. Le raccourci gardé billeterie est refusé tant qu’une ligne automatique `auto_fee=ticketing` (ou une copie « Frais de billeterie » non retouchée) est active. La ligne automatique reste 25 € par voyageur, libellé « Frais de billeterie (N billets) » : le raccourci ne l’écrase pas et ne la retire pas. Son libellé n’est pas « Frais de billeterie », donc `syncTicketingFee` ne le prend pas. Retirer la ligne automatique (`fee_mode=ticketing_off`) rend le raccourci de nouveau disponible. Train et transfert n’ont pas cette garde. La commission, si la case est cochée, porte sur le raccourci comme sur toute dépense saisie à la main, pas sur la ligne automatique.
- À l’import, `item.amount` reste null (le PDF va dans `document_amount`). Le montant du séjour reste 0 tant que l’agent n’a pas saisi le prix vendu de chaque carte. `sellingTotalFromExtract` = cette somme, jamais le total PDF.
- Import `document_status=confirmed` : `bookingStatusFromExtract` peut écrire `confirmed` (même si `from-ingest` envoie `draft`). Toujours `visible_to_client=false` jusqu’à **Montrer au client** : le débit part à ce geste, pas à l’enregistrement.
- `customer_id` du débit = `booking.billing_customer_id` (payeur / wallet), pas forcément le voyageur
- **Plusieurs sociétés** (`crm_billing_companies`) : attribution `billing_company_id` sur le séjour, la dépense et la ligne du livre. La vue `crm_customer_balances` reste un seul solde (crédits − débits `posted`). La répartition Société / Particulier est une lecture de ce solde, pas un second wallet. Transactions : libellé société **seulement** si le compte en a au moins deux. Une seule société → le nom suit « Société » dans la répartition. Dès qu’il y en a deux, la liste des réservations, le séjour et la carte Transactions disent quelle société règle (RB&A · Crédit ou Pro).
- **Crédit et Pro** (`funding` sur la société) : seulement si la fiche a **les deux**, `advance` et `pro`. Deux soldes, sans compensation. Un virement reçu (Revolut ou saisie) ne choisit pas le compte : l’agence l’indique à Valider. Sans ce choix, la ligne reste à rapprocher — l’auto ne la poste pas. Le crédit se dépense dans la limite du droit de dépense ; pas de carte ni d’Apple Pay dessus. Pro se règle dans l’app par carte ou Apple Pay, sans plafond. Un paiement Pro ne recharge pas l’autre compte. Sans ces deux marques, l’encours unique ne change pas. Une facturation ne supprime pas ces deux sociétés.
- `syncTicketingFee` : **25 € par passager** du dossier (`crm_booking_travelers`), dès qu’il y a un vol. Paris, 4 billets = 100 €. Plusieurs segments du même voyageur ne multiplient pas. Sans voyageur nommé : 25 €. La ligne est une **dépense** du dossier (`details.auto_fee=ticketing`, libellé « Frais de billeterie (4 billets) »), créée dans Dépenses. L’agence peut la modifier ou la retirer : la transaction (`external_id=booking:{id}:expense:{itemId}`) suit tout de suite. Une modification pose `fee_touched` et le calcul ne l’écrase plus. Un retrait pose `fee_mode=ticketing_off` et la ligne ne revient pas. Hors assiette de la commission. L’ancienne écriture `booking:{id}:ticketing-fee` est annulée. Sans vol, la ligne non modifiée disparaît.
- **Commission d’agence** : case du dossier, pas du virement. Taux sur le compte (défaut 10 %, ou 7,5 %, ou 5 %) et dérogation sur le dossier. Voir encours ci-dessus. Assiette = étapes actives (séjour + extras) + dépenses, hors frais de billeterie et hors crédits. Une ligne par réservation, recalculée quand une étape, une dépense ou le taux change. Le sélecteur n’est pas montré au client. Ce n’est pas la marge des devis e-mail.

Ajustements / remboursements : lignes manuelles admin `kind=adjustment|refund`.

## Stripe — règlement dans Transactions

- Le règlement est dans **Transactions** (`/mon-compte/transactions`), sous l’encours, libellé **Régler**. Le même bloc est en haut de la réservation. Société : carte, Apple Pay, prélèvement SEPA et virement. Particulier : carte, Apple Pay et virement.
- Le dossier a `payer_kind` : `company` (société, défaut = première `crm_billing_companies`) ou `personal` (particulier). L’agence le choisit dans Règlement pour ranger le débit. Le client ne choisit pas la société.
- `fees_follow_stay` (défaut true) : frais d’agence, frais de billeterie (25 € par passager dès qu’un vol est confirmé) et dépenses suivent la facture du séjour. L’hôtel réglé par le client n’est pas un encaissement.
- Part société : carte, Apple Pay, prélèvement SEPA et virement, en euros. Part particulier : carte, Apple Pay et virement, sans prélèvement. Hors euros : carte et Apple Pay seulement, pour les deux parts. Quand les deux parts sont dues, chacune a son bloc (nom, montant, pastilles). Le collaborateur `member` ne règle pas l’encours : il voit ses frais, le compte qui porte le wallet paie. Les moyens tiennent sur une ligne de pastilles ; le formulaire s’ouvre seulement pour le moyen choisi.
- Le grand livre reste un seul encours, sauf les deux comptes crédit / Pro ci-dessus. Chaque règlement crédite le wallet de la part. `payer_kind` range Société / Particulier. `billing_company_id` range le crédit ou Pro.
- `POST /api/client/ledger/pay` reçoit `payerKind` `company` ou `personal`. Le montant vient du serveur (la part due au moment du clic, pas un chiffre saisi). `POST /api/client/bookings/[id]/pay` répond 410. Carte et Apple Pay créent un PaymentIntent (moyens dynamiques, `excluded_payment_method_types`). Pas de PAN / CVC. Apple Pay = portefeuille Stripe. Le libellé du crédit porte la part.
- Prélèvement société : le bouton **Lancer le prélèvement** confirme un PaymentIntent `sepa_debit` avec l’IBAN déjà enregistré sur la fiche (pas de ressaisie). Sans IBAN français valide, ou si Stripe refuse, le client voit pourquoi et la suite (Facturation, carte ou virement). Le particulier n’a pas de prélèvement : le message le dit. Une part qui ne correspond pas au solde (particulier alors que seul la société est due, ou l’inverse) est refusée avec le montant dû. Dès que le PaymentIntent est `processing` (ou qu’une charge SEPA est `pending`), un crédit `pending` du grand livre réserve le montant : l’encours affiché tombe de cette part, sans être un encaissement `posted`. Bannière « Prélèvement SEPA en cours », ligne d’historique « Prélèvement SEPA · en cours ». Un second prélèvement de la même part (`payer_kind` + `billing_company_id`) est refusé tant que le premier n’est pas `succeeded`, `payment_failed` ou `canceled`. Carte et virement ne reprennent pas le montant réservé ; seul un surplus (nouvelle dépense) reste payable. `requires_payment_method` ne réserve rien. S’il existe un prélèvement `processing` du même montant, les PaymentIntents `requires_payment_method` de ce client sont annulés. On n’annule jamais un `processing`. Succès : le crédit passe `posted`, libellé « Payé le … par prélèvement SEPA ». Échec : la réservation est retirée, l’encours revient, message français et alerte agence. Fonds insuffisants : on peut réessayer. Compte fermé, mandat révoqué, IBAN refusé : un nouveau RIB, pas le même mandat. La lecture de l’encours relit Stripe (prélèvement déjà lancé, webhook manqué). Pas d’e-mail ni de WhatsApp à cette occasion. Une contestation ou un remboursement prévient l’agence et ne crée pas un second avoir.
- Virement = compte **Revolut Business** (IBAN SEPA du compte euros actif nommé **Main**), pas Stripe `customer_balance`. La route ne crée pas de PaymentIntent. Elle renvoie IBAN, BIC, titulaire, le montant de la part et le **nom du client** comme référence, et elle prévient l’agence (alerte Paiement, fiche et transactions). Ce n’est pas un prélèvement : le client doit virer, l’agence rapproche dans À encaisser. Jamais d’IBAN complet dans les logs ni les alertes (quatre derniers caractères au plus). Une poche au nom différent n’est pas proposée. Plusieurs comptes Main, ou aucun IBAN SEPA unique → le virement reste fermé et le dit. Sans compte Main, un seul IBAN euros distinct ouvre le virement.
- Le crédit du virement passe par l’inbox Revolut (sync / rapprochement), pas par le webhook Stripe.
- Webhook `payment_intent.succeeded` → crédit `source=stripe`, `external_id` = id du PaymentIntent, wallet = `crm_customer_id` des métadonnées. Un règlement d’encours n’a pas de dossier : `payer_kind` range la part. Un `pay_method=revolut` ne crédite pas. Pour le prélèvement, `payment_intent.processing` pose le crédit `pending`, `payment_intent.succeeded` et `charge.succeeded` le passent `posted`, `payment_intent.payment_failed`, `charge.failed` et `payment_intent.canceled` retirent la réservation. `charge.refunded`, `charge.dispute.created` et `mandate.updated` (mandat inactif) alertent l’agence sans second crédit. Le cron Stripe relit aussi les PaymentIntents pas encore `succeeded`.
- Les PaymentIntents `succeeded` entrent dans `crm_stripe_transactions` (cron `/api/cron/stripe-sync` tous les quarts d’heure, minute 7 ; bouton Synchroniser ; webhook). Premier passage : 14 jours. Ensuite : depuis le curseur, avec 6 jours de recouvrement (un prélèvement créé plus tôt peut réussir plus tard). Une ligne déjà identique n’est pas réécrite. Crédit strictement positif. Hors file : `pay_method=revolut`, montant nul, autre statut. Le `raw` ne garde que l’id, le montant, le statut, la description, l’e-mail, le customer Stripe, les metadata, le moyen et le last4. Pas de PAN.
- Déjà au grand livre (`source=stripe`, `external_id` = PaymentIntent) : la file passe `matched`, sans second crédit.
- Le payeur se lit dans cet ordre. E-mail : `billing_details`, reçu, session Checkout, client Stripe, facture. Nom : facturation, session, client, facture. Désignation : description, champs du lien, nom du produit, metadata. Le `raw` garde `customer_email`, `customer_name`, `checkout_session_id`, `payment_link_id`, `custom_fields`, `invoice_id`. Le client Stripe est mis en cache.
- Auto seulement si un seul hit certain : `metadata.crm_customer_id` ou un seul `stripe_customer_id` sur la fiche. L’e-mail, un client Stripe déjà vu sur un paiement rapproché, et une désignation de quatre chiffres (facture, devis ou pièce MB3M) sont des propositions : rien n’est crédité sans le clic. Plusieurs candidats : Argent › **À encaisser** (`/admin/argent?onglet=a-encaisser`, section Paiements Stripe) attend **Créditer** (confirmation), Choisir ou **Refuser**. Refuser = `ignored`, aucun crédit. Statuts à l’écran : À encaisser · Encaissé · Refusé.
- Compléter les payeurs (administrateur, `completer_payeurs_stripe`) relit Stripe pour les lignes ouvertes sans nom ou e-mail. Sans confirmer, aperçu. `confirmer` écrit seulement `payer_name` et `payer_email`. Un lien de paiement créé par le CRM exige l’e-mail du client et pose la référence du dossier dans les metadata.
- Crédit agent : `kind=card_payment` (carte, Apple Pay) ou `transfer` (prélèvement). Libellé « Règlement Stripe · {payeur} · {moyen} ». `payer_kind` et `billing_company_id` seulement s’ils sont dans les metadata. Déjà `matched` → 400.
- Les versements Stripe qui arrivent sur Revolut ne se créditent pas en bloc. Chacun est découpé en une ligne par paiement (brut, nom, e-mail, référence, dossier) plus une ligne de frais d’agence. Le clic Créditer pose le brut : c’est ce que le client a payé. Les frais Stripe ne deviennent pas un débit client. Un paiement déjà au grand livre (`source=stripe`, identifiant du PaymentIntent) est marqué « Virement Stripe (déjà encaissé via Stripe) », sans second crédit. La somme des lignes vaut le versement. Le détail Stripe est mis en cache sur la ligne, sans nouvel appel tant qu’il est complet.
- SetupIntent (`/api/client/stripe/setup-intent`) + `setup_intent.succeeded` → `crm_payment_methods`. `payment_method.detached` → delete.
- Pas de page cartes : `/mon-compte/profil/paiement` reste la facturation.

`getStripe()` absent → webhook 503. Le carnet, le grand livre et Revolut continuent. Le bouton de règlement indique que le moyen n’est pas ouvert.

## Revolut

Flux : API Business → `crm_revolut_transactions` (`unmatched`, **crédits seulement**) → matching → **proposition**. Aucun score (IBAN, nom complet, société, nom de famille) n’écrit un crédit. L’inbox et la fiche attendent **Valider** ou **Refuser**.

- `POST /api/admin/revolut/[id]` `{ customer_id }` | `{ action: "ignore"|"refuse" }`
- Déjà `matched` → 400
- Sync importe les **crédits** (topups / virements reçus) pour le rapprochement, et les **sorties complétées** (virement, carte, retrait, frais, change) dans l’onglet Débits. Un débit est `direction=debit` et entre en `status=unmatched` (**à rattacher** à un voyage) ; `matched` = rattaché comme coût ; `ignored` = **hors voyage**. Une synchro suivante ne touche pas au statut choisi. Jamais de crédit client. Une autorisation encore `pending` n’entre pas. Intérêts (`Intérêts Revolut`), virements entre comptes de l’agence, remboursements de carte et frais sont classés et sortent de la file, sans crédit. Un versement Stripe est découpé, pas proposé comme un seul encaissement client. `shouldIngestRevolutForRapprochement` / `shouldIngestRevolutDebit`.
- Cron `/api/cron/revolut-sync` (quart d’heure, minute 2) + webhook : depuis le curseur, 2 jours de recouvrement (14 jours au premier passage du cron, 30 au premier clic Synchroniser). ## Comptabilité du voyage (coûts, marge, MB3M)

Une sortie Pliant (achat, retrait ; remboursement et chargeback en négatif) ou Revolut (débit) est un **coût**. Une ligne vendue du dossier (débit `posted` : carte, dépense libre, frais, ou montant global « Séjour ») est une **vente**. Pointer = rattacher chaque coût à une ligne vendue, **au clic**. Marge par ligne = vente − Σ coûts, négative possible (affichée, pas bloquée). Le client ne voit ni coût ni marge.

- Table `crm_trip_costs` (`booking_id`, `booking_item_id` nullable = montant du séjour, `source` pliant|revolut, `source_id` = id de la ligne `crm_pliant_transactions` / `crm_revolut_transactions`, `amount_eur` signé, montant et devise d’origine, `supplier`, `occurred_on`). Unique (source, source_id). service_role seulement. Lib pure `lib/crm/trip-costs.ts`, accès `lib/crm/trip-costs-db.ts` (`attachOutgoing`, `detachTripCost`, `setOutgoingOutsideTrip`, `loadOutgoingQueue`, `loadTripAccounting`).
- **Pliant ne débite plus le client.** Plus de `source=pliant` au grand livre (historique passé en `void`, converti en coût quand le dossier était connu, sinon revenu dans la file). Argent › À pointer (`?vue=pliant`) et le bloc Carte Pliant (onglet Argent) du dossier proposent **Rattacher** ; la carte du dossier propose le dossier. `match_status` : `unmatched` à rattacher, `matched` rattaché, `ignored` hors voyage.
- **Carte Pliant** (Argent › À pointer › Toutes les dépenses Pliant, mobile et bureau) : pastille **À pointer** tant que la dépense n’est pas sur un dossier. La proposition du moment a **Accepter** et **Refuser** (Refuser l’écarte, la dépense reste à proposer). **Rattacher à un dossier** cherche par référence, titre, destination, prénom, nom, société du client, société facturée et voyageurs (sans accent, mots dans n’importe quel ordre), puis une ligne (ou le montant du séjour). L’autocomplétion montre la référence, le lieu, les dates, le client et la société. **Changer de dossier** et **Détacher** (dialogue) : Détacher remet À proposer, retire le coût, laisse la vente. Une dépense, un dossier : le montant ne se partage pas. Chaque geste est dans `crm_trip_cost_events` (qui, quand, dossier d’origine, dossier d’arrivée, sans numéro de carte). Le statut Pliant Comptabilisée est le règlement de la carte, distinct de À proposer. `link_released` empêche la synchro de recoller une dépense détachée sur la carte du dossier.
- Revolut garde aussi `matched_booking_id`, `matched_customer_id` (payeur du dossier) et `settled_at` (date du clic) : « hors voyage » pose `settled_at`, sinon `repairRevolutDebitQueue` remet la ligne dans la file. Détacher vide `matched_booking_id` (trigger → `unmatched`). Les outils MCP `rapprocher_depense_revolut` et `rapprocher_pliant`, la route `/api/admin/bookings/[id]/pliant` (plus appelée par l’écran ; le bloc Coûts du voyage passe par `/api/admin/comptabilite`) créent le même coût, sur le montant du séjour.
- Rattacher : d’abord une carte existante, sinon **Nouvelle dépense** (libellé + prix vendu pré-rempli = coût, modifiable) créée `kind=expense`, `include_in_ledger`, cachée au client, puis `refreshBookingLedger`. Plusieurs coûts par ligne. Coût sans ligne au livre = « coût sans vente ». Revolut hors euros : l’agent saisit le coût en euros (`eur_amount`). Déjà rattachée → 409.
- Propositions, jamais écrites (`suggestCostTargets` / `rankCostTargets`). On n’affiche une piste que si les indices se recoupent : référence du dossier, carte Pliant du dossier, PNR, montant exact (ou 3 % d’écart de change), compagnie et date du vol, hôtel et lieu (pas la marque seule : Edition, Six Senses), noms des voyageurs, e-mail de confirmation. Le nom de compagnie est une expression entière (« El Al », « ELAL ») ou son code IATA dans un numéro de vol (LY315) : « el » et « al » seuls ne comptent pas, et « Hôtel Almenara » n’est pas El Al. La date Pliant affichée est l’autorisation (`createdAt`), pas le débit. Compagnie seule, marque seule ou petit montant (bagage, siège) : aucune proposition. Le coût net fournisseur dans sa devise (supplier_net) est le montant du débit carte. Un même chiffre seulement cité dans un autre e-mail ne crée pas une seconde piste. Chaque piste dit pourquoi, les voyageurs et la confiance (haute, moyenne ou faible). Deux sorties au même commerçant et au même montant : la seconde reprend le même dossier en confiance faible, motif « Montant déjà proposé pour une autre sortie – doublon possible. » Une autorisation Pliant encore en attente entre dans la file seulement si une piste existe. Un refus (DECLINED) ou une annulation (REVERSED) n’est jamais une sortie à rattacher. Une autorisation CONFIRMED reste proposée tant qu’aucun débit BOOKED du même commerçant et du même montant, à sept jours, n’existe sur le même dossier ou une carte de ce dossier, y compris s’il est déjà rattaché. Sinon elle disparaît de la liste du dossier et reste dans la file générale avec « Couverte par le débit du … ». Rien n’est rattaché tout seul et aucun coût n’est créé. Avant octobre 2026, une carte Pliant porte le nom du client (libellé, pas le collaborateur agence) : Amadeus, Hôtel, Club Med et TB-AAAA-NNNN ne comptent pas. La fenêtre est [création du dossier − 14 jours, fin du séjour + 7 jours], séjour inclus si le dossier a été saisi après. Parmi les séjours de ce client, on départage d’abord par le n° de confirmation (Expedia, ou la fin du n° dans un libellé EG*TRVL), puis le fournisseur ou l’hôtel, puis le montant, puis le lieu (SJO ou Costa Rica contre Miami), et seulement ensuite la date. Un dossier sans dates reste proposé si la confirmation ou le fournisseur correspond. Motif « Même client / même carte. ». Un hôtel ou un montant d’un autre client ne l’emporte pas. Un n° de confirmation (EG*TRVL ou une longue suite de chiffres déjà dans confirmationRef) propose le dossier en confiance haute sur n’importe quelle carte, y compris la carte agence, même si le débit n’est que la part Expedia et reste inférieur au coût net. La part Expedia écrite dans la note ou un champ dédié compte aussi comme montant. Plusieurs débits identiques du même itinéraire : le suivant est signalé « doublon possible ». Un remboursement (montant positif) suit la même règle. L’agence clique Rattacher. La piste, le bloc de confiance et le choix de dossier nomment le titre, le titulaire et la société, pas seulement TB-AAAA-NNNN. Rien n’est rattaché tout seul. Une sortie Pliant dont la carte a été générée depuis un dossier porte `cardInfo` (dossier d’origine, porteur, plafond, validité, pays, clôturée) affiché sous la ligne ; score ≥ 90 (`isSureSuggestion`, référence ou carte) = « Quasi certain », ligne surlignée champagne (`lineIsSure` dans `OutgoingAttach.tsx`). **IATA / BSP** (`IATA ESPAGNA SL`), **virement de trésorerie vers Pliant** (bénéficiaire `Travel Business Agency`, désignation `treso Rev - pliant`) et **virement entre comptes de l’agence** (`From treso`, `To treso`, `treso`, `EUR Main`, `From EUR …`, virement interne Qonto, ou transfert Revolut à deux jambes sans contrepartie externe) : `isOwnAccountTransfer` / `isSettlementParty` → aucune proposition, la sortie n’apparaît dans aucun dossier. IATA et la trésorerie restent dans Argent › À pointer pour **Hors voyage**. Le motif « Le nom du fournisseur correspond » n’est posé que si un mot du bénéficiaire est celui du fournisseur, ou le commence (au moins 5 lettres) : « treso » n’est pas dans « Phuket Resort ». Une dépense Pliant d’une carte de dossier est un coût dès l’autorisation (`state=pending`, hors marge MB3M) et se confirme au règlement. **Coûts fixes** (`isFixedCostParty` : OpenAI/ChatGPT, Cursor, Vercel, Google, Anthropic/Claude, Perplexity, eSIMo, Free en tête du libellé) : ni proposés ni montrés, `loadOutgoingQueue` et `pendingCostLines` les sautent ; la ligne reste `unmatched` en base.
- Écrans : bloc **Coûts du voyage** (`components/admin/TripCostsBlock.tsx`) sur l’onglet Argent du dossier (`?tab=argent` ; `?tab=reglement` y mène), qui remplace les anciens blocs Cartes Pliant + Comptabilité du voyage : une seule file « N sorties à rattacher » (sorties proposées + dépenses Pliant des cartes du dossier encore `unmatched`, dédoublonnées par `source:id` dans `lib/crm/trip-cost-lines.ts`) avec le même `OutgoingRow` / **Rattacher** que `/admin/comptabilite` (dossier fixé, **Hors voyage** via `allowOutside`), puis les cartes Pliant du dossier (rattachée · ligne, Retirer, Hors voyage → Remettre dans la file), les lignes vente/coût/marge/facture, les coûts sans vente avec **Déplacer** (boutons par ligne vendue, `retarget`, pas de select natif), les débits Revolut rattachés sans coût posé, les anomalies, l’état **À pointer / Pointé / Comptabilisé**. Rattacher un débit du dossier à un autre voyage passe par Argent › À pointer. En tête de l’onglet, `ReglementSummary` lit `reglementChecklist` (`lib/crm/reglement-checklist.ts`) ; `staffBlockingChips` ajoute « N coûts à pointer » et « Marge à corriger » (chips qui ouvrent Argent). Onglet Argent › À pointer : toutes les sorties non rattachées, filtres source et période, Rattacher, Hors voyage ; hors voyage se remet dans la file depuis les vues Toutes les dépenses Pliant / Toutes les sorties Revolut. API `POST /api/admin/comptabilite` (`attach` par défaut, `move`, `refuse`, `detach`, `outside`, `restore`), `GET /api/admin/comptabilite/cibles?q=`. MCP `comptabilite_voyage` (lecture : chaque coût porte `cout_id` et `sortie_id`). `detacher` accepte `sortie_id` seul si un seul coût est lié.
- **MB3M** : MB3M facture **Net + Marge**. `NetPriceUnit` est donc **vente − marge** (le net fournisseur) et `MarginUnit` la marge (`mb3mInvoiceLine`) ; envoyer la vente en net ferait une pièce gonflée de la marge (25 071 € vendus → 29 636 € facturés). Sans coût pointé, la marge est la vente entière — mais **MB3M refuse un net à 0** (-504 « Une erreur s'est produite durant l'enregistrement de la facture », code interne -20505) ; les types `Fees` (« non supporté ») et `Note` (marge comptée, ligne absente du PDF) ne conviennent pas. `mb3mInvoiceLine` met donc un net plancher `MB3M_MIN_NET = 0.01` et la marge qui complète (vérifié sur la base partners : la pièce imprime le bon montant). Vol Amadeus = activité 2, billet acheté sur le site de la compagnie = 1001, low cost sur ce site = 27. Ces trois activités ne partent pas : l’écran dit « billetterie en attente de la mise à jour API MB3M », tant que `MB3M_FLIGHT_COMMISSION` n’est pas 1. Le code prépare alors `CommissionId` (activité 141 : 1 international à 0 %, 6 France à 0 % ; activité 147 : 44 France à 0 %, 45 international à 0 %). Le train part en 5, sans champ de commission. Les frais d’agence sont des lignes Custom (LineType 4, code 401 billetterie, 12 hôtel, 13 tourisme, 4 remise), fournisseur = l’agence, sans marge. Un net à 0 reste au plancher d’un centime, la marge complète, le TTC inchangé. Le message affiché reprend `Details`, pas seulement le texte générique. Une facture sans numéro n’est verrouillée que si `attempt_status=preparing` depuis moins de 3 minutes. Un échec (API, coupure) écrit `attempt_error` et `failed` : le clic suivant reprend la même fiche et le même dossier MB3M. Pastille **Préparation en cours** ou **Préparation échouée**, message « Préparation en cours (démarrée à HHhMM par X), réessaie dans N min » ou la dernière erreur, bouton **Reprendre**. L’ancienne pro forma s’annule **après** la création de la nouvelle. `Note` « Fournisseur : … ». Chaque prestation porte le `ProviderId` d’un fournisseur déjà dans le catalogue (`lib/crm/mb3m-providers.ts`) : compagnie par code IATA, hôtel selon la source (Hôtels divers, Little Emperors, CDS, Expedia), train SNCF / OUIGO direct / TRAINLINE. Transavia, y compris Transavia France, est TRANSAVIA. S’il manque, la facture ne part pas, la raison s’affiche, et un e-mail part à marie@travelba.fr. Aucun fournisseur n’est créé. Un frais d’agence porte l’Uid de l’agence de la pièce. Un vol dont le PNR est déjà la référence (`RefCommand`) d’une facture MB3M importée d’Amadeus n’est pas remis sur la facture CRM : la phrase est « déjà dans MB3M via Amadeus (facture n°…) ». La recherche part même si la fiche n’est que sur la pièce (`customer_uid`), pas seulement dans `crm_mb3m_parties`. Une erreur Amadeus ou de règlement fait échouer la préparation, et cette erreur reste lisible sur la pro forma déjà numérotée. ChangeFolder est `IPieceService/ChangeFolder` : Uid de la pièce (bloc `Identity`, pas le client ni le dossier qui précèdent), numéro, puis `NewFolder` (Id et Uid du dossier). Si MB3M refuse le déplacement (facture fournisseur soldée, ou tout autre refus), la préparation continue : la facture Amadeus est liée au séjour (`kind` gds), son PDF imprimé est visible au client, le vol reste hors de la facture CRM, et l’avertissement est renvoyé par la préparation et par le statut, y compris quand la pièce est déjà en place. Aucun second lien, PDF ou règlement. `IFolderService/ChangeFolder` n’existe pas. Le PDF d’une facture Amadeus est demandé à MB3M même sans date d’impression. S’il revient, il est déposé sur le dossier, visible au client. Sinon l’avertissement dit que l’API ne l’a pas rendu. Le CRM n’imprime pas la pièce. Une pro forma ouverte dont les lignes changent est annulée ; si l’annulation échoue, la nouvelle pièce est retirée et la préparation échoue. Les règlements déjà saisis se lisent par FindAllPieces (`IncludePayments`), pas par FindPayments. Sans ce PNR, la ligne reste. La facture sans dossier est rangée dans le dossier du séjour ; une facture déjà dans un autre dossier ne bouge pas. Les crédits se lettrent d’abord sur la facture CRM, puis sur ces factures Amadeus. Préparer la facture enregistre aussi les crédits postés du client comme encaissements MB3M (`SavePayment`, virement Revolut, Qonto ou carte Stripe, référence `CRM` + identifiant) puis les lettre sur la pièce (`WriteMatching`), au plus pour le reste dû. Un collaborateur (`company_role` member, `billing_parent_id` = l’admin société) est payé par les crédits de ce compte, et par ceux des autres collaborateurs de la même société : sans dossier, ou déjà posés sur ce dossier. Un crédit posé sur un autre dossier n’est pas pris. Un crédit sans dossier n’est envoyé comme nouveau règlement que s’il n’y a pas d’autre séjour ouvert ; un règlement MB3M déjà là (même montant et même jour, comme le 2149) est adopté et seul son reste est lettré. Le dossier n’est posé sur le crédit que s’il y tient en entier. Le mode envoyé est une valeur de PaymentMode du WSDL Partners (`None`, `BankTransfer`, `BankOrder`, `OnlinePaymentCard`, `PaymentCard`, `Check`, `Cash`, `Custom`). Virement, Revolut et Qonto sont BankTransfer ; Stripe et un paiement en ligne sont OnlinePaymentCard ; une carte physique est PaymentCard ; un chèque est Check ; des espèces sont Cash ; un prélèvement ou un ordre est BankOrder. « Carte virtuelle Pliant » est Custom seulement si un CustomModeId est déjà configuré, sinon PaymentCard. Un mode inconnu part en None, avec un avertissement. Si la facture a encore un montant dû et qu’aucun reste n’est trouvé, la préparation enregistre un avertissement au lieu d’une liste vide. Le mode vient du rattachement : `crm_trip_costs.instrument` (`pliant_card` + `instrument_detail` = 4 derniers chiffres ; `revolut_transfer` / `revolut_card` / `revolut_other` d’après `raw->>'type'`), libellé `settlementLabel` = « Carte Pliant ···· 5454 », « Virement Revolut », « Carte bancaire Revolut », affiché en tête de chaque coût dans `TripCostsBlock`. Les signatures du 15/10/2026 ont porté un `:§règlement` une heure ; `mb3mPieceStale` l’ignore. ## Soldes des comptes

Le tableau de bord (`/admin`, bloc **Comptes**) et la page de chaque compte montrent le solde, comme Pliant (« Solde du compte »).

- **Revolut** : le tableau de bord montre les comptes actifs **Main** et **Trésorerie**, en euros. La trésorerie est une poche d’épargne absente de `GET /accounts` (`account_type` `other` ou `savings`, nom `SP:…`) : on la retrouve dans les mouvements déjà synchronisés, puis on lit son solde. Le libellé est **Trésorerie**. Les autres poches (devises, comptes nommés) restent sur Argent › Comptes, euros d’abord, Main puis Trésorerie. Inactif ignoré. Pas d’IBAN. Non connecté : la carte n’est pas affichée.
- **Stripe** : le tableau de bord montre le montant **en attente** de versement (`balance.pending`, centimes → euros). Le disponible reste sur Argent › Comptes, en grand, avec l’attente en dessous. Pas de body brut.
- **Pliant** : `availableLimit` de l’organisation, déjà sur la page Pliant, repris sur le tableau de bord.

Compte non ouvert : pas de carte. Appel en échec ou trop long : **Indisponible**. Le zéro est un solde réel.
